# Product and Sprint Backlogs

The backlog evidence comes from the [Pulse Guard Trello board](https://trello.com/b/L3GWnqCP/pulse-guard-project) and its exported snapshot. The [Trello evidence page](evidence/README.md) includes the board overview and numbered sprint screenshots.

## Product Backlog

The Product Backlog groups work across discovery and research, UX design, architecture, backend services, mobile development, dashboard development, testing, and deployment. Its cards include supporting tasks such as creating wireframes, mapping APIs, configuring authentication, connecting screens to backend data, handling loading and error states, and testing across devices and browsers.

The export also contains checklist breakdowns for research, UX, architecture, backend development, testing, and deployment. The mobile and dashboard frontend cards list implementation work from project setup through navigation, data integration, interface states, and quality checks.

### Product Backlog reflection

The 17 April logbook entry records that I cleaned up the Product Backlog before drafting user stories. Reviewing that entry beside the board helped me see how broad project areas become more manageable when each has smaller tasks. The board covers the full path from discovery and design through development, testing, and deployment. I also learned that a backlog is useful only when its priorities and status are clear: the export contains detailed task checklists, but some card descriptions and parent-card statuses do not agree. I would keep task breakdowns connected to the user need and review priority and status with the team during planning.

## Sprint Backlog

The board records technical and design tasks in sprint lists 1–8. Examples include wireframes and architecture in Sprint 1, prototypes and database design in Sprint 2, API and backend work in Sprint 3, security and mobile setup in Sprint 4, mobile integration and testing in Sprint 5, and dashboard development across Sprints 6–8. The board also has story-focused sprint lists that continue through Sprint 26, including deployment in Sprint 25 and testing in Sprint 26.

The [numbered screenshots](evidence/README.md#numbered-sprint-screenshots) show the later sprint lists, from Sprints 6–26. The dated logbook entries do not identify sprint numbers, so this portfolio does not assign the April or August entries to a particular sprint.

### Sprint Backlog reflection

The sprint cards show work moving through research, design, architecture, backend and frontend development, and testing. This helped me see how a sprint backlog breaks a larger product goal into work the team can act on. The export uses overlapping Sprint 1–8 numbering for different sets of cards, so it is difficult to read as one continuous sprint history. The later cards name deployment and testing goals, but the dated logbook does not connect its entries to sprint numbers. I learned that sprint goals, task ownership, and results need to be recorded alongside the cards so that progress can be reviewed without guessing.

## Snapshot note

The supplied export contains 40 checklists with 198 checklist items marked complete. Some parent cards remain open or contain status wording that conflicts with their checklists. This page reports the checklist and card information separately; a checked item is not treated as proof that its parent feature was released.
